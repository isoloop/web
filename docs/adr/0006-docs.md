# ADR 0006: Docs

- **Status:** Accepted (2026-11-20)
- **Date:** 2026-11-20
- **Answers:** how the library's docs reach `isoloop.dev` (pages, rendering, highlighting, the files for agents, the API reference, search), and how the docs keep matching the code as features are added, changed and removed. Grilled 2026-11-20 (Q1–Q31) as [`isoloop/isoloop` M4c](https://github.com/isoloop/isoloop/blob/main/docs/plans/m4c-docs.md). Covers `isoloop/isoloop` and `isoloop/web`, as [ADR 0004](0004-publishing-and-governance.md) does. Amends [ADR 0002](0002-site-build.md) (decision 12) and [ADR 0005](0005-page-navigation-and-status-marks.md) (decision 1a, the header). Extends ADR 0004 (decisions 2, 4 and 6).

## Context

0.1 needs docs that people and agents can read. Until now, ADR 0002 decision 12 left the docs to M4: they render into this site's shell, through an interface we own, with at most one dependency behind it and a conformance suite.

What exists today:

- **The library has six guides** in `docs/guide/`: agents, balancer, devtools, hosting, inspection and pools. Each has its own shape. The material for the guides still to write (getting started, isolates, the bus, contracts and grants, supervision, what Isoloop can't hide) is spread over the README, the ADRs, the system design and the investigations.
- **The TSDoc has gaps.** As of `0.1.0-next.7`, `createKernel`, `Kernel`, `KernelConfig`, `IsolateHandle`, `defineIsolate`, `isoloop()` and `createTestContext` have no top-level comment, and no export has `@example`. The published `.d.ts` rollups come from tsdown and keep the comments that exist.
- **Nothing checks the guides' code.** About 17 code fences and about 37 relative links in the six guides are checked by nobody.
- **The site already has parts the docs can use:**
  - its own build-time tokenizer (`apps/site/src/pages/code.tsx`, for TypeScript with JSX and for shell), which emits token classes and ships no highlighter;
  - the library pin (`apps/site/library.lock`) and `build/library.ts`, which checks out only `docs/diagrams` at the pin;
  - `packages/ui` (Header, Callout, Table and others);
  - the link check, axe and the CSP `default-src 'self'` (ADR 0002, decision 8).
- **ADR 0004's gates cover docs only loosely.** The definition of done says "docs for anything public: the guide or TSDoc". The library's API check fails a public `.d.ts` change without a change under `docs/` or in TSDoc. The steward judges whether the docs match. None of this says what a guide looks like, or which guide a change touches.
- **Most changes are made by agents.** As ADR 0004 found, instructions alone get followed most of the time, not every time. The docs need the same mix: mechanical checks where possible, and the steward's judgement where not.

## Decision

### 1. Where the docs live and what they show

- **The guides stay in `isoloop/isoloop`,** in `docs/guide/`, so they still read well on GitHub. The site fetches them at the library pin, as it does the diagrams. `build/library.ts` checks out `docs/guide` and, from phase B, `docs/api` as well as `docs/diagrams`.
- **The pin is a published version.** Until 0.1 it's the commit of a `chore: version 0.1.0-next.N` PR; from 0.1 it's a `v*` tag. The site's CI checks that the package versions at the pin are on npm. So the site never describes an API that `@next` doesn't have yet. *Today's pin, `3c354e8`, is the commit before `0.1.0-next.7`'s version PR, so the first docs build moves it.*
- **Bumping the pin stays a mechanical steward PR** after each publish (ADR 0004, decision 6). The docs go live only with a `site-v*` tag, on the maintainer's word.
- **One version.** No versioned docs before 1.0, and no redirects for removed pages.

### 2. Pages and navigation (amends ADR 0005, decision 1a)

- **The docs are at `/docs/`,** one page per `/docs/<slug>/`, with an index at `/docs/`.
- **The header's nav becomes Home, Features, How it works, Examples, Docs,** with GitHub still at the far end, beside the theme switch.
- **Each page has a section sidebar and a table of contents** built from its h2s. On phones the sidebar is a `<details>`. All of it works without JS (ADR 0002, decision 8).
- **The layout is mocked first:** one docs page, with the sidebar, TOC, a code block, a table and a callout, in both themes and at phone width. The maintainer approves it before the build. One direction, not alternatives.
- **The sections and their pages:**
  - **Start:** Getting started (with an `AGENTS.md` snippet for users' own apps), What Isoloop can't hide.
  - **Build:** Writing isolates, Contracts and grants, The bus, Supervision and restarts, Pools, Balancer, Hosting.
  - **Agents and tooling:** Agents, Inspection feed, Devtools panel, Build a dev tool as an isolate.
  - **Reference:** one API page per package, the CLI, and Kernel config as a link to the generated `KernelConfig` section (decision 7).
- **Writing isolates is one page,** with a section each for vanilla (`@isoloop/dom`), Preact and React. The parts they share are written once. It has no code tabs, so it reads the same as `.md` and in `llms-full.txt`.

### 3. Rendering (amends ADR 0002, decision 12)

- **`markdown-it` is the one dependency.** It sits behind our own `renderMarkdown(src) → { html, title, description, headings, links }`, with a conformance suite. Its token stream gives heading ids, the TOC and link rewriting without plugins.
- **Highlighting is our own.** The tokenizer in `apps/site/src/pages/code.tsx` gets json and html, and its TypeScript-with-JSX mode is tested on tsx. No highlighting dependency.
- **No front matter,** so the guides stay clean on GitHub:
  - The title is the `# h1`.
  - The description, used by `llms.txt` and the link preview, is the first paragraph: one sentence of at most 200 characters.
- **The order and the sections come from `apps/site/content/docs.json`.** The build fails if a fetched guide isn't listed, or a listed one is missing.
- **Links are rewritten at build:**
  - relative links to other guides become `/docs/…` URLs;
  - links to ADRs, plans, investigations or source become GitHub links at the pinned sha;
  - a relative link that resolves to nothing fails the build.

### 4. Files for agents

At every `site-v*` deploy, the build writes:

- **`/llms.txt`** in the llmstxt.org format: an H1, a one-line summary, then a section per docs section, with each page's `.md` link and description. An "Optional" section links the examples hub and the library's README. The library's "build with Isoloop" skill is linked once it exists.
- **`/llms-full.txt`:** every guide in nav order, then the API and CLI reference once they exist.
- **`/docs/<slug>.md`:** the fetched source, with its links made absolute.

CI checks that every docs page appears in `llms.txt` and has its `.md`.

### 5. Who writes the docs (extends ADR 0004, decisions 2 and 6)

- **The agent that makes a change writes its docs, in the same PR,** following the library's `docs` skill. It's the reason ADR 0004 gave for publishing: a separate writer would have to rediscover the context from the diff.
- **The `docs` skill** is `isoloop/isoloop`'s `.claude/skills/docs/SKILL.md`. It holds:
  1. the page types (guide, generated reference) and the guide skeleton;
  2. what each kind of change means for the docs:
     - **new feature:** a section in an existing guide, or a new guide;
     - **changed behaviour:** the sections that describe it;
     - **renamed or removed export:** every page that names it;
     - **new limit found:** "What Isoloop can't hide";
  3. the docs map, and how to add, rename or remove a page (the guide, `docs.json` here, the pin);
  4. the TSDoc rules (decision 7);
  5. the checks to run before a PR.
- **One guide skeleton:**
  - `# Title`
  - the one-sentence lead
  - `## When to use it`
  - the body, in task order
  - `## Limits`
  - `## See also`

  The six existing guides get one pass to match. Reference pages are generated, never hand-edited.
- **The writing rules have one home,** `isoloop/isoloop`'s `docs/writing.md`. It covers:
  - plain English, short sentences and bold lead-ins on bullets;
  - British spelling;
  - neutral language: measurements with device, build and tag, never "faster than native";
  - a list of banned phrases.

  The `docs` skill, the steward and the user-facing skill all point to it. This repo's `docs/brand.md` keeps the messaging for marketing copy.
- **The steward reviews docs** against `docs/writing.md` and the `docs` skill on every PR. Its Monday routine gains a docs drift pass: every guide read against the code on the library's `main`, with at most a few fix PRs.
- **The user-facing skill and the `AGENTS.md` snippet are docs too.** They go through the same map, checks and review.
- **Who approves:**
  - Edits to existing pages inside a feature PR merge on green CI and a steward pass. The maintainer reviews after, as for forks' code.
  - These go to the maintainer before merging: new pages, removed pages, restructures, `docs/writing.md`, the `docs` skill and the user-facing skill.
  - Docs-only PRs in the library still go to the maintainer, as its `AGENTS.md` says.

### 6. Mechanical checks (extends ADR 0004, decision 4)

- **The docs map,** the library's `docs/guide/map.json`, lists for each guide the source paths and exports it covers.
  - **A notice:** a PR that changes a mapped path without touching that guide gets a CI notice naming the guide. The steward judges whether it needed a change.
  - **Coverage, which fails:** every user-facing package and every public export appears in at least one guide's map, or is listed as reference only.
- **`pnpm docs:check`,** our own script in the library, runs in CI and in the pre-`gh pr create` hook. It fails on:
  1. a lead sentence that's missing or over 200 characters, or a missing skeleton section;
  2. a `ts` or `tsx` fence in `docs/guide/` that doesn't type-check against the workspace packages (` ```ts nocheck ` opts a fragment out);
  3. a relative link that resolves to nothing;
  4. a banned phrase from `docs/writing.md`;
  5. a guide that names an export the API check reports as removed or renamed;
  6. a gap in the map's coverage;
  7. an export without TSDoc at decision 7's bar, from the API freeze on.
- **Removing a feature:**
  - The API check flags the removal.
  - Item 5 fails while any guide still names it.
  - If a whole page goes, its `docs.json` entry is removed here in the same session, with Site impact `update needed`.

### 7. The API reference

- **Our own generator,** in the library, reads each package's published `.d.ts` rollup with the TypeScript compiler API, so it documents exactly what ships.
  - It writes `docs/api/<package>.md`, committed. CI fails on drift, as the diagrams' test does.
  - The site renders those pages like any guide, at `/docs/api/<package>/`, and `llms-full.txt` takes them as they are.
- **One page per user-facing package,** with a section per entry point: host (with `./dev-mcp`), runtime, bus, dom, react, preact, vite, balancer, devtools and webmcp. protocol and codec are left out. The protocol types that host re-exports are documented under host.
- **What the pages show:**
  - Symbols tagged `@experimental` get the Experimental pill (ADR 0005, decision 4).
  - The kernel config reference is the generated `KernelConfig` section of the host page.
  - The CLI page is generated from `packages/cli/src/args.ts`, so a new flag can't be missing from it.
  - Each symbol links to the guides that list it in the map. There's no hand-written `@see` to guides, so the link has one source.
- **Complete TSDoc,** filled in by the API freeze (`isoloop/isoloop` M4d task 1), with `docs:check` item 7 landing in it:
  1. every exported function, class and const has a lead sentence, `@param` for each parameter, `@returns` when it returns something, and `@throws` naming its error codes;
  2. every field of an exported options or config type has its own comment, with its default;
  3. the main entry points have an `@example`, type-checked like the guides' fences: `createKernel`, `defineIsolate`, `topic`, `contracts`, `isoloop()`, `kernel.request`, `connectDevtools`, `connectWebMCP` and the balancer's entry.

### 8. Search

- **Our own, with no dependency,** after the API reference.
- **The index:** a build plugin writes `/docs/search.json`, with titles, headings, section text and API symbols. It's about 40–90 KB gzip, loaded only when the search box gets focus.
- **The search box:** a module of about 200 lines. It ranks title over heading over body, and works from the keyboard and a `/` shortcut. Without JS the box is hidden.

## Consequences

**Good**

- The docs on the site always match a version on npm, and the guides on GitHub match `main`.
- A rename or removal in the API fails CI in the guides that name it, instead of leaving a stale page.
- One skeleton and one writing guide, checked mechanically where they can be, so docs written by different agents read alike.
- The reference can't miss an export or a flag, since it's generated from what ships and the TSDoc check makes every export documented.
- The same Markdown serves GitHub, the site, the `.md` copies and `llms-full.txt`, so there's no second copy to keep in step.
- One new dependency (`markdown-it`), behind an interface with a conformance suite; highlighting and search stay our own.

**Bad**

- More per PR: a change to a mapped path brings a notice to answer, and the fence check asks fragments to compile or be marked `nocheck`. Too many `nocheck`s would defeat it.
- The map's notice is judgement, not a gate. A guide can still drift where no mapped path changed; the weekly drift pass is the backstop.
- The site shows docs only as fresh as the last published version and the last `site-v*` tag.
- The generator and `docs:check` are our own code, to keep working as TypeScript and the packages change.
- Our tokenizer highlights less precisely than a full grammar.

## Alternatives considered

- **TypeDoc** (with its Markdown plugin) for the reference: many dependencies, and a theme to fight to match the site.
- **api-extractor:** a large dependency for what our `.d.ts` rollups already give; ADR 0004 turned it down for the API check for the same reason.
- **`unified` and `remark`:** dozens of packages for features we don't need.
- **`marked`:** no dependencies, but weaker hooks for heading ids, the TOC and link rewriting.
- **Shiki:** emits inline `style` attributes, which `default-src 'self'` blocks, and it's large.
- **highlight.js:** fits the CSP with class output, but it would be a second dependency behind the docs, against ADR 0002 decision 12, when our tokenizer already covers most of what the docs show.
- **Pagefind:** its WebAssembly needs `'wasm-unsafe-eval'`, which `default-src 'self'` doesn't allow.
- **A separate docs-writer agent:** it would rediscover the context from the diff, and copy written from diffs drifts, as ADR 0004 found for publishing.
- **Front matter in the guides:** it shows up as a table on GitHub, and the h1 and the first sentence already carry the title and description.
- **Versioned docs before 1.0:** there's one prerelease line, and nobody to serve an older version to yet.
- **Code tabs per framework on Writing isolates:** nicer to look at, but they read worse as `.md` and in `llms-full.txt`.
